Проблемы многопоточности в сетевых серверах

Введение

Модель thread-per-connection проста: сервер принимает TCP-соединение и создаёт отдельный поток для его обслуживания. Пока один поток блокируется на recv(), другие клиенты могут обслуживаться независимо.
Но такая модель сразу создаёт две группы проблем: синхронизацию общего состояния и корректное завершение ресурсов.

Гонка данных

Если несколько потоков изменяют один общий счётчик без синхронизации, операции могут пересекаться. Из-за этого итоговый счётчик может оказаться неверным.
В сервере общий client_count защищён pthread_mutex_t. Изменение счётчика выполняется между pthread_mutex_lock() и pthread_mutex_unlock(). Поэтому два рабочих потока не изменяют его одновременно.
Тот же мьютекс защищает связанный список клиентов. 

Утечки файловых дескрипторов

Сетевой сокет является файловым дескриптором. Каждый успешный accept() создаёт новый дескриптор клиента. Если не вызвать close(), сервер постепенно исчерпает лимит открытых дескрипторов.

В рабочем потоке после окончания работы выполняется:

shutdown(client->fd, SHUT_RDWR);
close(client->fd);

При остановке сервера главный поток сначала вызывает shutdown() для активных клиентов. Это позволяет разблокировать рабочие потоки, находящиеся в recv(). После этого главный поток ждёт их через pthread_join().

Корректное завершение

Просто завершить процесс недостаточно для хорошего серверного кода. Нужно прекратить приём новых подключений, разбудить рабочие потоки и дождаться их завершения.

В проекте сигнал SIGINT или SIGTERM устанавливает флаг остановки и закрывает listening socket. Из-за этого accept() прекращает ожидание. Главный поток выходит из цикла, вызывает shutdown_all_clients(), затем делает pthread_join() для завершившихся рабочих потоков.

Так ресурсы освобождаются в определённом порядке.

Почему мьютекс не нужен для всего

Мьютекс следует использовать только там, где действительно есть общее изменяемое состояние. 

Если начать блокировать один общий мьютекс вокруг всей сетевой работы, один медленный клиент может задерживать остальные подключения. Это уменьшает преимущество многопоточности.

Итог

Thread-per-connection удобен как учебная модель и подходит для небольших серверов, однако количество потоков растёт вместе с количеством соединений. Для большого числа клиентов обычно рассматривают event-driven архитектуру, пул потоков или асинхронный ввод-вывод.

Главные правила безопасной реализации:

1. защищать общий изменяемый счётчик мьютексом;
2. явно владеть каждым файловым дескриптором;
3. закрывать клиентский сокет во всех путях завершения;
4. при остановке разбудить блокирующие рабочие потоки;
5. дождаться созданных потоков через pthread_join();
6. не держать общий мьютекс во время долгих сетевых операций.
